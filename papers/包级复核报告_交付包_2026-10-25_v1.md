## 2 · 复核方法（为什么这些命令够）包级复核要证的不是"包看起来对"，而是**第三方只拿这个包能不能独立重建并验证**。我的五个核验面：

1. **清单全量核对**（不是抽样）—— 内容完整性

4. **无 git 原地重建** —— 证明包**自包含**、可被第三方独立重建
5. **交付态复跑验收工具** —— **在"解包后的那棵树"上**跑，而不是在仓里跑

 第 5 条是 v1 的结构性缺口（我发现的 S-01），也是 v2 的重点。

### 3.2 · v1 的三条发现

#### P-01 ｜ 应修 ｜ 包内 `tools/check_docx.py:151` ＋ 打包器的成员时间戳策略

**问题**： **解包后跑包内自带的 `check_docx.py`，EXIT=1，11 个文件被判「docx 比 md 旧」**，**包的自证链在交付态断在这里**（内容本身没问题：清单 197/197 逐字节相符，**假红**）。

**根因链（逐环节实测，不是推测）**：
```
① 可复现打包 ⇒ 成员 date_time 固定 (1980,1,1) ⇒ zip 不携带真实 mtime
     zip 内 06_L3 成员的 date_time: (1980, 1, 1, 0, 0, 0)
② zipfile.extractall() 把每个文件的 mtime 设成【解包时刻】（不是 zip 里的 date_time）
     ⇒ 解包后 mtime 由【解包顺序】决定
③ 成员顺序按名字排序 ⇒ .docx 排在 .md 之前
     # 16  papers/06_L3_层3自修改_交差稿.docx
     # 17  papers/06_L3_层3自修改_交差稿.md
     ⇒ docx 的 mtime 比 md 早 1 ms
④ check_docx.py:151  用 getmtime 比较 ⇒ 判红
     实际 mtime:
     papers/06_L3_层3自修改_交差稿.md    mtime=2026-10-24 23:41:51.119654497 +0800
     papers/06_L3_层3自修改_交差稿.docx  mtime=2026-10-24 23:41:51.118654465 +0800
```
 被红 11 个：`01_L1`／`02_A`／`04_D`／`06_L3`／`08_回源对照表`／`审稿回执_方向3层3`／`改稿报告_A`／`改稿报告_L3`／`终审后修复报告`／`终审报告_外部审稿意见逐条复核`／`终审报告_方向3层3`。

** 根因定性**： **判据与打包器在语义上打架** —— 「docx 不比 md 旧」是**基于文件时间戳**的判据，在一个**刻意不携带时间戳**的可复现包里**必然可能假红**；且**不是换解包顺序能修的**（任何解包工具／任何顺序都可能踩）。

**修复建议**： **推荐 ①：build 时把【源 md 的 sha256】写进 docx**（docx 本身是 zip，可塞条目或 `docProps`），`check_docx.py` 改用**内容指纹**判新鲜度，**与时间戳彻底解耦**，且**对第三方更可核**（第三方能自己算 md 的 sha 再去 docx 里对）｜② 次选：解包态把该判据**降级为告警**｜③ **单纯调成员顺序：治标且不稳，不建议**。

#### P-02 ｜ 应修 ｜ 包内 `tools/pack_papers.sh` 的 `--repro` 段（第二段内嵌 python）

**问题**： **`--repro` 自检在交付态必然崩**：
```
$ bash tools/pack_papers.sh <out.zip> --repro
fatal: not a git repository (or any of the parent directories): .git
fatal: not a git repository (or any of the parent directories): .git
Traceback (most recent call last):
  File "<stdin>", line 35, in <module>
NameError: name 'src' is not defined
```
**两个缺陷叠加**：
- 第一段（正常打包）的循环里**有** `src = os.path.join(tree, n)`，**第二段（`--repro`）没有**，第二段的 `with open(src, "rb")` 用了从未定义的 `src`
- 第二段**没有 git 回退**（直接 `os.popen('git ls-files -z')`，无 try/except、无目录遍历回退），即便修好 `src`，无 git 环境下第二个包内容只剩 2 个 EXTRAS，**会误判「不可复现」**（第二处假红）

** 诊断层次**：这不是"少了一行"，而是**同一条要求在第二个执行点没落实** —— owner 自己刚立的「**断言必须回头读产物**」在第一段做到了（源码里明确注释"zip 关闭前读到的 `zinfo.flag_bits` 是【中间态】…，断言一律放到【产物写完之后回头读产物】"），但**第二段既没做产物级回读、也没做 git 回退**。

**修复建议**： **合并成一条代码路径，不是补那一行** —— 真正逻辑收敛到 `tools/pack_papers.py` 的唯一一份 `build()`，`pack_papers.sh` 只做转调，打包与 `--repro` 共用同一条路径，**不可能再分叉**；顺带那份"第二段没有 git 回退"的问题也一起消失。

#### S-01 ｜ 建议 ｜ 包内 `tools/check_package.py` 的包级自检清单

**包级自检没有覆盖「解包态的 docx↔md 双向自检」**，**这正是"四道闸全绿"的来源：第四道闸是在【仓里】跑的，不是在【解包态】跑的**，建议包级自检加第五项：解包到临时目录后跑一遍 `check_docx.py`，这样 P-01 这类"只在交付态出现的红灯"**不可能再漏过**。

**这与 owner 自己刚立的「断言必须回头读产物」是同一条要求的另一个面：断言必须在【交付态】读，不是在【生产态】读。**
