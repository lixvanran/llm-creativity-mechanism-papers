## 3 · 这一轮我自己的一个新发现：**包不能自证自己的 sha**

 v2 给 R-07 的建议是「用 `SHA256SUMS.txt` 自身的 sha 作**非循环身份锚点**」（方向对），**但它同时建议把这个值写进入口文档**（它举的例子是 `984ee931…`），**这一步是错的**，我按原建议做就会制造一个新的过期数字。

**为什么错（自指悖论）**：

```
入口文档  ──写──▶  清单  ──覆盖──▶  入口文档
   ▲                                        │
   └────────────── 改一个值就变 ─────────────┘
```

 `SHA256SUMS.txt` 覆盖其余全部成员、**自身不入清单**，它的 sha 稳定标识**整包内容集**，**这没错**；**错在把它写进包里**：写进去，改这个值，改入口文档，改清单，改锚点，**值自己把自己改了**，**只能是环**。

**做法（本包就是这么做的）**：
1. 入口文档**声明锚点的【算法】**：`sha256sum SHA256SUMS.txt`（不写死值）；
2. 入口文档**说明为什么不写死**（上面那段自指）；
3. 同理，**本包自己的 sha256 与字节数也不写死在包内**（那是**外部事实**），入口文档只给**上一版 / 被审版**的 sha 作参照。
4.，**可复算、可核、不可能过期**，这比"写死一个值"强，因为**写死的值必然会过期，而算出来的值不会**。

**原则**：**凡是「自指」的量（对象自己的指纹 / 自己的大小 / 自己里指向自己的指针），只能【声明算法】，不能【写死值】。**

## 4 · 元教训：**「读出来」不等于「抄对了」**

 这一轮写补丁脚本时，第一版用「old_string → new_string」精确匹配，**3 条替换串匹配不上**，而 Read 工具给出的内容**看起来**和文件完全一样。

**根因**：**Read 的输出是给人看的，不是给机器匹配的**，我手抄了 3 处长串，抄的时候把某个全角标点抄成了另一个，**肉眼在两处都看不出差别**。

**做法（已写进脚本头注）**：**按【行号】替换**（行号从文件里数出来，不经人手抄），**手抄错误彻底消失**，代价是脚本一次性（应用后行号漂移），补偿：加**幂等守卫**（重跑时判「是否已应用过」，安全退出而不是报错）。

**另一条同源的要求**：**审计人 v2 的 §0.2 写的是同一件事**（他自己数行数时先踩了一次坑： `split('\n')` 与 `wc -l` 差 1，11 处引用全"差 1"），**「数字对不上」的第一嫌疑永远是【自己的口径】，不是文档过期**，**先固化口径，再判死**。
