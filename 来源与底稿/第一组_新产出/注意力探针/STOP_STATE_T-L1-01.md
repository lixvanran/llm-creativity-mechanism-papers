## 2 · 失败原因（★ 已定位到行 ★）

**根因是本单自己写的日志抽取代码的一处 dtype 不匹配，★ 不是模型失败、不是 OOM、不是镜像拉不到、不是内存爆 ★。**

```
File "scripts/03_probe_run.py", line 156, in run_one
    raw = model.lm_head(h.unsqueeze(0)).squeeze(0).float().numpy()
RuntimeError: expected m1 and m2 to have the same dtype, but got: float != c10::BFloat16
```

- 崩在**生成之后**、**反解 raw logits** 那一步（★ 生成本身是成功的 ★）——
  `h` 被我 `.float()` 成 float32，而 `lm_head` 的权重是 **bf16** ⇒ matmul 的两个操作数 dtype 不一致。
- ★ **与「探针」本身无关**：注意力权重、hidden states、logits 都已经拿到手了，★
  **只是把它们转成熵的那一行写错** ★。

### 已定位、★ 但**未验证**的修法（★ 停止令之后没有再跑批，所以没有验证过 ★）

```python
# scripts/03_probe_run.py · run_one()
-  h = hss[k][-1][0, -1].detach().float()          # ← 错：float32 喂给 bf16 的 lm_head
+  h = hss[k][-1][0, -1].detach().to(model.lm_head.weight.dtype)
   raw = model.lm_head(h.unsqueeze(0)).squeeze(0).float().numpy()
```

★ **为什么写成 `.to(weight.dtype)` 而不是「保持 bf16」**：transformers 5.x 的 `output_hidden_states`
末层**可能是 float32** ⇒ 「保持原 dtype」不一定对；★ **转成权重 dtype 对两种情形都成立** ★。
★ **接手的人请在第 0 批上先验这一行再铺开 9 批**（★ 别像我一样一次铺 9 批才发现 dtype 不对 ★）。

## 3 · ★ 一次过程事故（★ 必读：它会污染留痕 ★）

★ **我把同一份日志和同一批单元，让两次运行同时在写** ★ —— 起因是我在第一次运行还活着的时候
就启动了第二次（修 bug 后重跑），而两次用的是**同一个日志文件名**、**同一个输出文件名**。

| 现象 | 后果 |
|---|---|
| 两次运行并发写 `logs/batch00.log` | ★ **该日志是两份交错的**，**不能当作单次运行的证据** ★（故本目录另存了它，仅作事故留痕） |
| 第一次运行的输出文件被 `mv` 走之后，它**仍按 inode 继续追加** | 故那份文件里有 **11 条**（不是 6 条）记录 |
| 第二次运行的落盘文件 | ★ **在停止时丢失**（目录为空）★ |

★ **后果对读数的影响：零**（本来就没有成功的单元）★；**后果对留痕的影响：日志交错、须谨慎解读** ★。

★ **教训（写给下一个跑长跑的人）** ★：
> **长跑必须「互斥锁 + 带批号的独立日志文件名 + 带批号的独立输出文件名」。**
> ★ 否则一次「重跑」会与前一次**串味**，留下的日志既不能当证据、也读不出真实进度 ★。

★ 另注：本沙箱的 `bash` 调用**超时会把该次调用的进程组一起杀掉** ⇒
`timeout 1500` 护住的是**前台那一段**，而**外层 harness 的 180 s 截断仍会把长跑掐掉** ⇒
★ 接手的人**必须用真正脱离会话的方式起长跑**（`setsid` + 立即返回 + 后续只看**落盘行数**判断进度，
★ 不要看进程在不在 —— 「空输出」≠「没有进程」）★。
